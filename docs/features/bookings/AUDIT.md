# Phase 04 — Booking & Scheduling Audit

> Scope: booking requests, session scheduling, recurring classes, guardian
> multi-child access, conflict prevention, cancellation/rescheduling, calendar
> export, reminders, and the payment boundary.
>
> Audited at commit `a2e6ca3` against the running local PostgreSQL database
> (`ogroniedu_dev`, PostgreSQL 18, 18 migrations applied).

## 2. Findings (severity ordered)

### P0 — Payment boundary is bypassable

- `PaymentsService.sandboxConfirmOrder()` fabricates a webhook payload and
  calls the webhook processor. It has no environment, role, or ownership guard,
  and the controller exposes it to any authenticated user.
- The booking pay page calls `sandboxConfirm` and renders success from local
  state, not from the authoritative booking/order status.
- `SslcommerzSandboxAdapter.verifyWebhookSignature()` accepts unsigned bodies
  whose `status` is `VALID`/`VALIDATED`/`succeeded`.
- `SslcommerzSandboxAdapter.queryTransaction()` falls back to a fabricated
  `succeeded` result when the provider cannot be reached.
- `BkashSandboxAdapter` has the same signature bypass and an always-succeeded
  `queryTransaction()`.
- `SessionSchedulingService` auto-confirms `accepted|awaiting_payment`
  bookings when a session is scheduled, so a booking can become `confirmed`
  without any payment.

### P0 — Booking status transitions are unchecked

There is no transition map. Each service checks a single current status and
then assigns the next status inline (`bookings.service.ts`,
`payment-webhooks.service.ts`, `session-scheduling.service.ts`,
`session-rescheduling.service.ts`, `trust` replacement flow). There is no
per-booking status history table; only generic audit logs exist.

### P1 — Availability is never enforced

`tutor_availability` is written by `TutorProfileService.setAvailability()` and
read by the public profile, but scheduling never consults it. There is no
date-specific blocked-period table. A tutor can be booked outside their stated
hours.

### P1 — Recurring classes are not a real series

- No series entity; occurrences cannot be addressed as a group.
- Generation uses `new Date(dto.startDate + 'T00:00:00+06:00')` and slices
  ISO strings, hard-coding Asia/Dhaka and relying on server-local behavior.
- `count` drives a `while` loop with no horizon bound; an unsatisfiable slot
  set loops forever.
- A retry creates a duplicate batch; no idempotency key.
- There is no per-occurrence availability/exception check and no partial-failure
  reporting.
- There is no this-occurrence / this-and-future / entire-series operation.

### P1 — Reminders and outbox are dormant

- `OutboxWorkerService.processPendingEvents()` is only invoked from tests.
- No scheduler or interval calls it, so durable events never leave the table.
- `session.reminder` has no generator. `startSession()` reuses the event for a
  "class started" message, which is semantically wrong (the template says the
  class starts in 30 minutes).
- `outbox_events` has no unique/idempotency constraint and `notifications` has
  no dedupe key, so a retry can double-deliver.

### P1 — Guardian child isolation is incomplete

- `getRequests()` returns every request visible to a guardian, including all
  children mixed together; the UI has no child selector.
- `getSessions()` accepts `studentId` but silently returns an empty list for a
  child that is not linked; there is no explicit revalidation error.
- The sessions page has no child scope at all.
- Cache keys for request lists are not child-scoped.

### P2 — Calendar export semantics

- `formatIcsDate()` converts to UTC (correct instants) but the file claims
  `X-WR-TIMEZONE:Asia/Dhaka`, which is misleading.
- Every event is emitted with `STATUS:CONFIRMED` or `CANCELLED` but without
  `SEQUENCE` / `LAST-MODIFIED`, so updates and cancellations do not propagate
  reliably to Google/Apple.
- Meeting URLs (which may contain join tokens) are embedded in `DESCRIPTION`.
- Lines are not folded at 75 octets.
- The endpoint returns JSON, not a `.ics` download response.

### P2 — Session lifecycle guards are weak

- `startSession()` permits `in_progress` (idempotent) but does not check the
  booking's authoritative status.
- `completeSession()` has no status guard at all; a cancelled session can be
  marked completed.
- `updateMeetingUrl()` has no status guard.
- `completeSession()` does not roll the booking to `completed` when the last
  session finishes.

### P2 — Duplicate-request race

`createRequest()` performs a check-then-insert with no DB constraint. Two
concurrent identical requests both pass the check. A partial unique index is
needed.

### P3 — Repo/phase numbering

The prompt file is `prompts/09-booking-and-scheduling.md`, while this delivery
is tracked as Phase 04. The canonical requirements live in
`docs/13-booking-and-scheduling.md`. This is documentation-only and does not
affect behavior.

## 3. Existing invariants to preserve

- PostgreSQL GiST exclusion `ex_tutor_session_overlap` on
  `tstzrange(starts_at, ends_at, '[)')` for statuses
  `scheduled|in_progress`.
- `GuardianAccessService` is the single home for guardian-link and booking
  access checks.
- Notification registry is the single source of event types/roles/copy.
- All money is integer minor units (`bigint`), never floats.
- Cancellation policy percentages are assessments only; no refund/ledger
  mutation happens in the booking flow.
